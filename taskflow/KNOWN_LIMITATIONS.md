# Taskflow — Known Limitations & System Boundaries

This document provides a factual assessment of the prototype implementation, distinguishing fully implemented features from runtime constraints, background delivery limitations, and future architectural scope.

| Area | Current Implementation State | Technical Reality & Impact | Documented Recommendation / Follow-up |
|---|---|---|---|
| **Authentication & Authorization** | Fully Implemented | JWT Bearer tokens signed with HS256 (`pyjwt` / `python-jose`). Passwords hashed with standard `bcrypt`. Full ownership verification enforced on every user-owned model (`user_id` query filters preventing cross-tenant leakage). | Add token revocation blocklist / Redis store for immediate logout revocation if invalidating JWTs before expiry is strictly required in high-security environments. |
| **Database Persistence** | Fully Implemented | SQLAlchemy 2.0 ORM with Alembic schema migrations (`001_initial_schema.py`). Supports PostgreSQL target (`postgresql+psycopg2://` / `asyncpg`) and SQLite local development. | In production, deploy on PostgreSQL 15+ to leverage native JSON/check constraints and table partitioning if task volume grows to millions of rows. |
| **Reminders & Scheduler** | Implemented (In-Process) | Background polling via `APScheduler` (BackgroundScheduler checking every 60s) and deduplicated in-app `notifications` table (`UNIQUE (reminder_id, fired_date)`). | **Limitation**: In-process background scheduler runs only while the FastAPI server process is running. If backend stops, due reminders are queued until next startup. For guaranteed enterprise delivery, use Celery/Redis or cloud queue (AWS SQS, GCP Cloud Tasks). |
| **Browser Push Notifications** | In-App Inbox Implemented | Due reminders create persisted in-app notification rows fetched via `/api/notifications` with unread badge counter and mark-as-read toggle. | Native Web Push API (Service Worker with VAPID keys) is reserved for future P2 scope; notifications currently require an open browser session with polling/re-fetching. |
| **Daily Missions Aggregation** | Fully Implemented | Pure aggregation query combining date-filtered tasks (`deadline` or `scheduled_start`) and active routine occurrences. | Computed in real-time without duplicate task generation, preserving single source of truth. |
| **Focus / Anti-Slump Support** | Fully Implemented | Returns actionable, supportive micro-step suggestions via `/api/focus-support/suggestion`. | **Verified non-mutating**: Guaranteed to not silently alter task state, deadline, or priority in database (verified by `test_tc18_focus_support_does_not_mutate_task`). |
| **Progress Metrics** | Fully Implemented | Computed dynamically from persisted `Task` completion timestamps and `RoutineLog` records across selected date range. | No synthetic counters or unpersisted local storage states (verified by `test_tc17_progress_summary_derives_from_persisted_records`). |
| **Performance & Load Testing** | Functional / Smoke Tested | 8-endpoint sequential flow benchmarked with genuine metrics (10.51 req/s sequential throughput, ~550 ms bcrypt login latency, ~25-50 ms CRUD latency). | Prototype has been evaluated under smoke/functional load (10 loops, 80 samples). High-load concurrent stress testing (e.g. 500+ concurrent virtual users) requires dedicated production database cluster and connection pooling. |
